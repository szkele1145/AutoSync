常见问题

按现象查。每条都给出原因 → 排查步骤 → 处理。

1. 客户端报 Connection reset（连不上更新源）

现象：更新窗口日志里出现 Connection reset / SocketTimeoutException / ConnectException / 更新源不可用，同步失败。

绝大多数情况是服务端根本没在跑，或者中间那段网络没通。

排查顺序（从内到外，一层层来）

# ① 服务端进程在不在？服务端机器上执行：
#    独立版：看 systemd（或前台窗口）
sudo systemctl status autosync --no-pager
#    MCDR 版：看 MCDR 日志
grep -i "AutoSync ✔ MSFP" logs/MCDR.log | tail -3

# ② 端口在不在监听？服务端机器上执行：
ss -lntp | grep 8123         # Linux
# Windows：Get-NetTCPConnection -LocalPort 8123 -State Listen

# ③ 服务端本机能不能连上？
python3 -c "import socket;s=socket.create_connection(('127.0.0.1',8123),3);s.sendall(b'PING\n');print(s.recv(64))"
# 期望：b'OK 0\n'

# ④ 从内网另一台机器测（排除隧道问题）
nc -vz <服务端内网IP> 8123

# ⑤ 从公网测（这才是客户端走的路）
nc -vz mc.example.net 8123

哪一步断掉就是哪一层的问题：

断在哪一步 原因 处理
① 进程不在 服务没启动 / 启动就崩了 看 journalctl -u autosync -n 50（独立版）或 MCDR 日志。常见是 config.json 写坏、端口被占
② 没监听 端口配错 / tcp_enabled: false 检查 config.json 的 tcp_host / tcp_port / tcp_enabled，改完重启服务
③ 本机连不上 服务崩了或监听在别的端口 同 ②
④ 内网不通 本机防火墙 Linux sudo ufw status；Windows 加防火墙规则（见 部署-Windows.md）
⑤ 公网不通 云安全组没放行 / frpc 没跑 / frpc 的 localPort 配错 控制台安全组放行 remotePort；systemctl status frpc；核对 frpc.toml 的 localIP / localPort / remotePort

其它可能

  • 客户端 urls 写错：不要写 http:// 前缀，格式是纯 主机:端口（例如 mc.example.net:8123，不是 http://mc.example.net:8123）。
  • DNS 解析问题：把域名换成 IP 试一次，能通就是 DNS。
  • 连接数打爆隧道：concurrent-files × download-threads 太大（默认 2 × 32 = 64 条），小带宽 frp 会拒绝新连接。先把 concurrent-files 降到 1 再试，见第 3 条。
  • 客户端和服务端版本不匹配：两边都应该是 1.0.0。协议是 MSFP v1，清单格式必须能对上。
  • 只有部分玩家报错：一般是玩家本机网络（公司/学校防火墙拦非标准端口）。让他换网络或用手机热点试一次，能通就是那个网络的问题。

2. 缺前置导致客户端崩溃

现象：玩家进游戏在加载界面直接崩，日志里有：

Missing or unsupported mandatory dependencies
Mod ID: 'xxx', Requested by: 'yyy'

原因：服务端的清单里少了某个被依赖的前置模组，玩家下载不到它，加载器直接拒绝启动。

第一步：在服务端找出到底缺什么

cd /opt/autosync/server

# 独立版
python3 -m autosync --base . deps

# MCDR 版（游戏内或控制台）
!!autosync deps

它会只读扫描 client-dist/mods 里所有 jar 的元数据（含 Jar-in-Jar 嵌套层），分成四类：

  • 真缺失前置 —— 有 mod 依赖它，但分发目录里没有；
  • JiJ 已提供 —— 依赖被某个 jar 内嵌了，不用管；
  • 无法解析 —— 元数据缺失/损坏；
  • 另有循环依赖与版本不匹配的单独提示。

第二步：自动补齐

# 看候选版本（不下载任何东西）
python3 -m autosync --base . deps-fix
# 输出会给出编号与候选，例如：
#   1  sodium            需要者 3 个   候选：1a 0.6.5 / 1b 0.6.4-beta
#   2  cloth-config      需要者 1 个   候选：2a 15.0.140

# 只装指定的两个
python3 -m autosync --base . deps-fix 1a 2a

# 或者一键全选推荐候选
python3 -m autosync --base . deps-fix apply

# 然后重建清单，让玩家能下到
python3 -m autosync --base . build

MCDR 版对应 !!autosync deps fix / !!autosync deps fix 1a 2a / !!autosync deps fix apply，然后 !!autosync build。

下载源策略：Modrinth 优先；Modrinth 定位失败时兜底 CurseForge（配了 curseforge_api_key 走官方 API，否则用免 key 的 CFWidget）。所有下载都会做哈希校验，同名不同内容绝不覆盖。

deps fix 的清单缓存 30 分钟，过期了重新跑一次。

第三步：防患于未然

  • 打开构建后自动检查：
"deps_check_after_build": true

这样每次 build 完都会顺手报告一次缺失前置（只告警，不阻断构建）。

  • 如果某个前置在 Modrinth/CurseForge 上都没有（自研 mod），把它手动放进 client-dist/mods/ 并写进 deps_fix_exclude 避免误下载。
  • 自动下载有大小上限（deps_fix_max_size_mb，默认 50MB），超限的会只报告不下载，需要人工处理。

3. 下载慢，怎么调

先说结论：客户端同时下载的连接数是乘积，调大不一定更快，隧道/家宽扛不住反而更慢。

最大连接数 ≈ concurrent-files × download-threads（小文件只占 1 条连接）。默认 2 × 32 = 64。

诊断：先分清瓶颈在哪

看客户端日志（游戏内窗口可复制，或 jar 同级目录的 mcpatch.log）：

日志里看到 瓶颈 对策
单个文件速度上不去，多个文件同时下也慢 单连接被限速 加 download-threads（32 → 48/64）
大量时间花在 SIZE / 建连等待，文件很碎（大量小文件） 文件级串行等待 加 concurrent-files（2 → 4，最多 8）
出现 Connection reset / 超时 / 重试 连接数超了，隧道或服务端扛不住 降低 concurrent-files（→ 1）和 download-threads（→ 8~16）
走 CDN 反而比服务端慢 CDN 到玩家那条路不好 source-mode: server（见第 6 条）
服务端 CPU/带宽打满 服务端瓶颈 让玩家走 CDN（source-mode: cdn），或升级带宽

参考档位

场景 concurrent-files download-threads 峰值连接
保守（小带宽 / 玩家多 / 隧道不稳） 1 8 8
默认（推荐） 2 32 64
激进（大带宽专线 / 玩家少） 4 32 128

其它能提速的开关

# 1) 优先用 Modrinth CDN 直链（把流量甩给官方 CDN）
source-mode: auto          # 或 cdn

# 2) 多源聚合：一个大文件的分块轮转分配到多个更新源
multi-source-download: true

# 3) 小文件不做分块（分段开销不划算）——保持默认 1MB 即可
download-threshold: 1048576

# 4) CDN 测速太慢时自动提线程重测
cdn-max-threads: 64

服务端侧

{ "poll_interval_seconds": 0 }   // 关闭定时检测，别让构建抢带宽
  • 确保 client-dist 和真实数据在同一块盘上（硬链接最省事，见 部署-Linux.md）；
  • frp 那边别开压缩（本就是压缩过的 jar，压了更慢）。

4. 玩家自己加的 mod 被清掉了

现象：玩家报告"我装的 XX mod 自己没了"，或者出现在 .modsync-removed/ 里。

原因：客户端开了镜像模式。

mirror-mode: true      # ← 罪魁祸首

mirror-mode: true 的含义是"客户端 mods/ 目录必须和服务端清单完全一致"：清单之外的一切文件都会被清理（包括玩家自加的性能 mod、自己换的附属、临时测试的 jar）。

处理

立刻改成 false（这是默认值，也是推荐值）：

mirror-mode: false
mirror-backup: true

改完后：
* 清单里列出的文件照常维护（缺的下、改的重下）；
* 清单之外的文件一概不碰。

对公共服 / 整合包：就应该用 false。玩家自加 Sodium、Iris 这类客户端优化 mod 是很正常的需求，镜像模式会把它们全清掉，投诉会很多。
只有确实要求"客户端必须和服务端一模一样、多一个文件都不行"（比赛服、反作弊服）时才开 true。

别忘了还有个兜底

即使不开镜像模式，detect-mod-conflicts: true（默认）会把与清单托管模组 modId 相同的玩家自加 jar 重命名为 xxx.jar.disabled，避免 NeoForge 因 Duplicate mod 崩溃。这是故意的设计，不是 bug；不想让它改名就设成 false。

5. 镜像模式误删文件，怎么恢复

先别慌，默认配置下文件还能找回来。

5.1 默认情况（mirror-backup: true）

清理不是"删除"，而是移动到：

<base-path>/.modsync-removed/

并且保留原来的相对路径结构。例如被清掉的是 mods/a.jar，那么它现在在：

<base-path>/.modsync-removed/mods/a.jar

<base-path> 是哪里：客户端配置里的 base-path 指向的目录。开了版本隔离时是 versions/<版本名>/，没开时是 .minecraft/。

恢复步骤：

  1. 先关掉镜像模式，否则下次启动又被清一遍：
mirror-mode: false
  1. 找到备份目录：
:: Windows：在版本目录里找
dir /s /b .modsync-removed
  1. 把想要的文件按原相对路径拷回去（备份目录里的结构就是原始结构）：
:: 例：把 mods 下所有备份恢复回去
xcopy /E /Y .modsync-removed\mods\* mods\

# Linux / macOS
cp -r .modsync-removed/mods/* mods/
  1. 启动游戏确认，确认没问题后再删 .modsync-removed/ 释放空间。

5.2 如果配了 mirror-backup: false

那就真的删了，只能靠：

  • 玩家自己的备份 / 整合包安装包；
  • Windows 的"以前的版本"（文件历史记录 / 卷影副本）；
  • 重新从 mod 的来源站下载。

所以强烈建议保持 mirror-backup: true（默认值）。

5.3 为什么会被误删

最常见的原因：服务端 dist_dir 配错，指向了一个几乎空的目录，构建出一份只有几项甚至 0 项的清单，客户端一同步就把别的文件都清理了。

客户端有一个兜底：清单里一个 mods/ 条目都没有时，绝不会执行清理，只打警告。但"清单少了一部分"是没法自动识别的。

预防措施（服务端侧）：

{
  "allow_empty_dist": false,        // 目录扫不到文件时构建直接失败，不生成空清单
  "poll_interval_seconds": 0        // 关掉无人值守的定时构建
}

每次 build 后习惯性看一眼输出里的"文件总数"和"待删除 N 条"，数字突变立刻停下来查。

6. CDN 与测速的流量代价

AutoSync 会在两个地方产生"额外"流量，都是客户端侧的（服务端只发清单，很小）。

6.1 多源测速（urls 有多个源时）

键 默认值 流量代价
auto-select-source true 每个源都要传一小段数据来评吞吐 + 延迟
source-probe-timeout 5000 ms 单个源的测速上限
source-speedtest-file speedtest.bin 服务端提供的 512KB 测速文件
  • 单个源最多传 512KB（speedtest.bin 的大小），2 个源 ≤ 1MB；
  • 结果会缓存 source-cache-seconds（默认 3600 秒），一小时内不会重复测速；
  • 不想付这份代价：auto-select-source: false（退化成按 urls 顺序依次尝试），或只配一个源。

6.2 CDN vs 服务端的选源测速

这部分代价大一些，因为要测"真实文件"的吞吐：

键 默认值 含义
speedtest-min-size-mb 10 只有 ≥ 10MB 的文件才会被挑来当测速样本
speedtest-duration-ms 2000 每个来源测 2 秒，CDN 与服务端并发测
cdn-max-threads 64 判定 CDN 太慢时把连接数翻倍重测一次
cdn-prefer-ratio 0.5 CDN 速度 ≥ 服务端的 50% 就直接选 CDN

每次同步开始时的最坏流量：

CDN 测 2s + 服务端测 2s（并发，各按当时速度下载）
    ≈ CDN 带宽 × 2s + 服务端带宽 × 2s
    ≈ 例如两边各 10MB/s → 约 40MB

如果触发了 cdn-max-threads 重测，这次流量再翻一倍（约 80MB）。

注意：这些测速流量是"真下载"——从 CDN 与你的服务端各拉了一段真实的模组数据，只是下完就丢，不写盘。

6.3 怎么把这份代价压下去

# 方案 A：完全不要 CDN，也就不需要选源测速（推荐给自建 CDN 被墙 / 服务端带宽充裕的场景）
source-mode: server

# 方案 B：完全交给 CDN，也不测速（推荐给服务端带宽小、玩家网络能直连 Modrinth 的场景）
source-mode: cdn

# 方案 C：保留 auto，但缩短测速窗口、提高选 CDN 的门槛
source-mode: auto
speedtest-duration-ms: 1000      # 从 2s 降到 1s
cdn-max-threads: 32              # 从 64 降到 32，重测更克制

source-mode: auto = 每次同步都测一次。如果你的玩家群体网络环境稳定，直接固定成 cdn 或 server（不用测速，零额外流量），只在换网络环境时才回到 auto。

6.4 走 CDN 时玩家侧的真实流量

选 CDN 意味着模组文件从 cdn.modrinth.com 下载，不消耗你的服务器带宽，但玩家的总下载量是一样的（该下的还得下）。AutoSync 的优化点是"少下"而不是"下得少"：

  • 清单里带 SHA-256，内容没变的文件不会重下；
  • 单文件分块 + 多线程，只是把同一份数据下得更快。

真正的省流量手段是别频繁重打包（每次重打包都会改变 SHA-256，玩家就得全量重下）。

7. Java 版本要求

项 要求
运行 AutoSync 客户端 Java 17 或更高（推荐 JRE 21）
编译 javaagent（开发者） JDK 17
支持的 Minecraft 版本 1.17 及以上（NeoForge / Forge / Fabric 均可）
1.16 及以下 不支持

为什么不支持 1.16 及以下

  • 1.16 及更早的版本普遍运行在 Java 8 上，而 AutoSync 的 javaagent 编译目标是 Java 17，Java 8 的 JVM 无法加载（会直接报 UnsupportedClassVersionError: class file version 61.0）；
  • javaagent 挂载时机与类加载器隔离规则在旧版本启动器/加载器上也有差异，即使强行换 Java 17 也不保证稳定。

怎么确认自己用的是哪个 Java

启动器的"Java 版本"设置里看，或者命令行：

java -version
# 期望：openjdk version "17.x" 或 "21.x"

启动器里一定要选 17 或 21，不要选 Java 8。

常见报错对照

报错 意思 处理
UnsupportedClassVersionError: ... class file version 61.0 用 Java 8 跑了 Java 17 编译的东西 启动器里把 Java 换成 17/21
Error opening zip file or JAR manifest missing : AutoSync-1.0.0.jar -javaagent 的路径不对 用相对路径 -javaagent:AutoSync-1.0.0.jar，并确认 jar 就在版本目录里
Failed to find Premain-Class manifest attribute 加载的不是 AutoSync 的 jar（文件损坏/换错） 重新下载 client/AutoSync-1.0.0.jar
完全没有同步窗口弹出，也没报错 JVM 参数没生效 检查启动器的"JVM 参数 / 自定义参数"里确实有 -javaagent:AutoSync-1.0.0.jar，且没有被别的参数覆盖
同步窗口弹出来但一闪而过 同步失败且 allow-error: true 关掉 allow-error，或看 mcpatch.log

8. 其它零碎问题

现象 处理
MCDR 报 Invalid entry point 'xxx' for plugin id 'autosync' 你装的是旧版/改坏了的包。重新用 tools/build-mcdr.ps1 打包，入口点必须是 autosync.entry
MCDR 报 Invalid JSON 加载插件失败 .mcdr 里的 mcdreforged.plugin.json 带了 UTF-8 BOM。重新打包（脚本写的是无 BOM UTF-8）
build 报"分发目录为空" 触发了 allow_empty_dist=false 的保护。检查 dist_dir 是否配对，不要急着改成 true
status 显示 0 个文件 同上，或者确实一个文件都没放
改了 config.json 不生效 独立版 serve 只读一次配置 → 重启服务；MCDR 版执行 !!autosync reload
终端中文乱码 chcp 65001（Windows）或确认 locale 是 UTF-8；程序会自动按终端编码降级符号
想去掉终端彩色 环境变量 NO_COLOR=1
.mcdr 解压后目录名怪 不要用 Windows 资源管理器解压；.mcdr 直接丢 plugins/ 即可。需要检查时用 python tools/check-mcdr-package.py
想跑测试确认代码没问题 python tests/run_tests.py（164 项，仅需标准库）
