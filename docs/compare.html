AutoSync 相比 McPatch2 的改动与优化

AutoSync 的客户端基于 BalloonUpdate/McPatch2 的 Java 客户端改造（MIT）。
本文逐条说明 改了什么、为什么改、解决了什么实际问题，全部有代码为证。

一、先说结论

McPatch2 是一套成熟、通用的整合包更新框架（HTTP / WebDAV / Alist 多协议、清单增量更新）。
但国内中小型 MC 服务器有几个绕不开的现实问题，AutoSync 就是冲着这些场景做的：

现实问题 常见做法 AutoSync 的做法
国内云服务器 HTTP 被 ICP 备案拦截（打开是"未备案"提示页） 依赖 HTTP / WebDAV / Alist 自研 MSFP 裸 TCP 协议，直接穿透
玩家版本不齐：自加 mod、残留旧 mod、手改文件 只做增量更新，剩下的靠玩家自觉 镜像模式：客户端 mods/ 强制与服务端清单完全一致
服务器带宽有限，几百 MB × 每个玩家 = 成本很高 全部从服务器拉 CDN / 服务端自动测速选源，能走 CDN 就走 CDN
同步出问题玩家只会说"进不去" 只有一个进度条 图形窗口实时日志，全程可见、可截图反馈
玩家自加 mod 与服务器模组撞 modId 导致崩溃 无检测 modId 冲突检测，自动禁用重复项
慢速网络下大文件下载体验差 单连接下载 多线程分块 + 文件级并发，实测 1.37 → 3.68 MB/s

一句话：McPatch2 给了框架，AutoSync 把它改造成了"国内服务器能直接用"的形态。

二、客户端：逐条改动

1. MSFP —— 自研裸 TCP 分发协议 ★核心改动

痛点

国内云服务器（阿里云 / 腾讯云大陆节点）对未备案域名或直接 IP 的 HTTP 访问会做拦截：浏览器/客户端拿到的是一个"未备案"提示页（响应头能看到 Non-compliance ICP Filing），而不是你要的文件。也就是说——HTTP 方案在国内云服务器上根本跑不起来，除非你去备案。

做法

自己实现了一套极简的裸 TCP 协议 MSFP（AutoSync File Transfer Protocol），不复用 HTTP：

GET <start> <end> <path>\n      →  OK <length>\n<data>      分块读取
PING\n                          →  OK 0\n                    存活探测
SIZE <path>\n                   →  OK <size>\n                取文件大小
  • 裸 TCP 不受 ICP 拦截影响（拦截的是 HTTP 层）
  • 协议极简：一轮一问一答，但支持 Range 分块、keep-alive、路径末尾放全文（含中文/空格/方括号的文件名不用转义）
  • 服务端做严格路径规范化，../../etc/passwd 这类越权访问会被拒绝
  • 客户端 sync/TcpFileClient.java 独立实现，与原有的 HTTP / WebDAV / Alist 协议并列，可按源切换

效果

不备案、不用域名，一台按量付费的云主机 + 一条 frp 隧道就能对外分发。

2. 镜像模式 —— 根治"客户端 mods 不干净"

痛点

增量更新的前提是"客户端只是缺文件"。但真实情况是：

  • 玩家自己加了一堆 mod（可能和服务器模组冲突）
  • 旧版本删掉的 mod 还留在 mods/ 里
  • 有人手滑改了文件名或删了文件
  • 整合包更新后，新旧文件混在一起

结果就是"服务端明明没这个 mod，客户端却加载了"，然后崩在某个莫名其妙的地方。

做法

新增 mirror-mode：客户端 mods/ 必须与服务端清单完全一致。

  • 清单外的一切文件（jar、.disabled、残留、玩家自加）→ 移到 .modsync-removed/ 备份而不是直接删除（给误操作留后悔药）
  • 清单内有、本地缺失或哈希不符 → 下载覆盖
  • 支持 mirror-backup: false 直接删除，或 mirror-mode: false 回到原来的增量模式（完全保留原版行为）

安全阀

  • 服务端清单为空时拒绝清理（防止配置错目录把玩家 mods 全清了）
  • 清理前校验分发目录结构，异常时中止

效果

玩家无论怎么折腾 mods/，启动一次就回到"和服务端一模一样"的状态。
这一条彻底消灭了「版本不一致」这一类问题。

3. CDN / 服务端自动测速选源 —— 省服务器带宽，但不牺牲速度

痛点

整合包动辄几百 MB 到 1 GB。全部从自己服务器拉：

  • 服务器带宽跑满，其他服务受影响
  • 玩家多的时候排队，下载很慢
  • 云厂商按流量计费的话，账单很痛

但直接"强制走 CDN"也不对——国内访问 Modrinth CDN 实测只有 ~0.24 MB/s，而自己的服务器（走 frp + 多线程）能到 3.6 MB/s，快 15 倍。玩家会骂人。

做法

每次同步开始时先实测一次，再决定走哪边：

① 挑一个 >10MB 的文件当样本（优先本次待下载的；都下好了就用"影子样本"）
② CDN 与服务端【并发】各下载 2 秒，算出各自速度
③ 判据：CDN 速度 ≥ 服务端速度 × cdn-prefer-ratio（默认 0.5）
     满足 → 走 CDN（差距不大时优先省服务器带宽）
     不满足 → 把 CDN 分块线程翻倍重测一次（上限 64）
              仍不满足 → 走服务端
④ 结果缓存 1 小时，期间不再重复测速

实况日志：

[测速] 样本 Flashback-0.39.10（201.0 MB，本次待下载）
[测速] CDN 3.21 MB/s  |  服务端 1.42 MB/s  ->  选 CDN（达服务端 226%）

[测速] CDN 0.31 MB/s  |  服务端 2.80 MB/s  ->  CDN 太慢，提升线程到 64 重测
[测速] 重测 CDN 0.55 MB/s  |  服务端 2.80 MB/s  ->  选服务端

"影子测速"是个刻意的设计取舍

需求原话是"如果样本不是待下载的，就删了重新下测速"。我们改成了影子测速：只读清单信息，从两个源各下一小段到临时文件，测完立即删除。

理由：为了测速去删玩家一个几百 MB 且已经是最新的文件，万一测速后断网/断电/被杀，文件就没了。测速不该有数据风险。

其它细节

  • 单连接 1 MB / 单来源 8 MB / 时长 2 秒，三层硬上限 —— 最坏情况（触发重测）额外流量约 24 MB
  • cdn-exclude 可指定哪些文件强制走服务端（Modrinth 上没有的自托管 mod 列在这里可少走弯路）
  • CDN 失败（404 / 哈希不符 / 超时）→ 自动回退服务端，同步不会中断
  • source-mode 可强制 cdn 或 server，也能一键关掉测速

4. 图形窗口实时日志 —— 出问题能自己看

痛点

同步过程是个黑盒：只有一个进度条，卡住了也不知道卡在哪。玩家反馈"进不去"，你只能让他发日志文件——很多人连 mcpatch.log 在哪都找不到。

做法

在原有的 Swing 窗口下半部分加了一个实时日志区（可拖动分隔条调整比例）：

  • 日志产生即滚动显示，自动跟到底部
  • 用户手动往上翻看历史时，新日志不会把视图拽回底部（翻回底部后自动恢复跟随）
  • 最多保留 2000 行（更早的看 mcpatch.log）
  • 统一单色、无边框、背景与窗口融合，滚动条 8px —— 视觉上"嵌进去"而不是"糊一块面板"
  • windowless 模式不弹窗（给无人值守/服务器用）

踩过的坑（值得一提）

  • Swing 的 DefaultCaret 会在稍后的另一个 EDT 任务里把视图拽到底，所以"只在追加日志时打标记"这种拦截方式根本无效 → 最终永久禁用 caret 的自动滚动，自己接管，并把 ↑↓/PageUp/PageDown/Home/End 显式绑到滚动条上
  • 判断"用户在不在底部"不能只看瞬时几何 —— 拖分隔条、缩放窗口、首次布局都会改变几何值而 value 不变，会导致判定瞬间失效并且永久不再自动滚动 → 改成记录"我们最后自动滚到的位置"，只要 value 还停在那儿就算仍在跟随

5. modId 冲突检测

痛点

玩家自加的 mod 如果和服务器模组用了同一个 modId，加载时会直接崩，而且报错信息很难懂。

做法

新增 sync/ModIdReader.java：读取每个 jar 的 META-INF/neoforge.mods.toml（回退 mods.toml），解析出 modId；发现重复时把玩家那一个重命名为 .disabled 并从加载列表排除。

镜像模式下这一层基本用不上（清单外的都被清掉了），但作为兜底保留。

6. 多线程分块 + 文件级并发

  • 单文件多线程分块：把一个文件切成若干段并发下载（download-threads，默认 32）
  • 文件级并发：同时下载多个文件（concurrent-files，默认 2）
  • 最大连接数 = concurrent-files × download-threads，默认 2 × 32 = 64
  • 小文件保护：CDN 路径下单个分段不小于 256 KB，1 MB 的小文件不会真的开 32 条连接

实测（4 个约 6 MB 的文件）：

线程数 耗时 速度
1 18.2s 1.37 MB/s
4 6.8s 3.68 MB/s
8 6.4s 3.89 MB/s

4 线程就是性价比拐点，再往上收益很小但连接数翻倍。

三、服务端：完全自研

原项目的管理端与本项目服务端是两套东西。本项目的服务端从零实现，Python 独立版与 MCDR 插件版共用同一套核心代码（构建时逐字节同步 + SHA-256 校验）。

能力 说明
清单生成 扫描分发目录 + SHA-256 + Modrinth 批量查询（命中率实测 80.7%）+ 内容指纹版本号 + 原子写入
MSFP 服务 多线程、keep-alive、路径规范化、流量与连接统计
测速文件 确定性生成 512 KB speedtest.bin 供客户端多源测速
模组分类 按 Modrinth 的 client_side / server_side 分类为纯客户端 / 双端 / 纯服务端，自动搬运（默认"只复制不移走"，并保护被依赖的模组）
依赖检查 解析 jar 元数据含 JiJ 嵌套层，找出真缺失前置、循环依赖、版本不匹配
缺失前置下载 从 Modrinth 下载缺失前置，支持 CurseForge 官方 API 与免 key 的 CFWidget 兜底，哈希校验 + 冲突不覆盖
双形态 server/python/（纯标准库，任意 Python 3.11+ 环境）+ server/mcdr/（MCDR 插件，命令树 / 权限 / 可点按钮）
输出风格 QBM 风格：彩色标题框 + ✔ ✘ ⚠ ℹ 状态标记 + 缩进键值列表
部署工具 SSH 增量上传 + 远端重建清单、跨平台 MCDR 打包脚本

四、这些改动带来的实际收益

以一个 150 个 mod / 817 MB 的整合包为例：

维度 改造前（传统 HTTP + 单源） AutoSync
国内云服务器可用性 ❌ HTTP 被 ICP 拦截 ✅ 裸 TCP 穿透
玩家版本一致性 靠自觉，经常崩 ✅ 强制镜像，每次启动校准
下载速度 1.37 MB/s（单线程） 3.68 MB/s（多线程）
服务器带宽占用 100% 从服务器拉 80.7% 的 mod 可走 CDN
出问题排查 让玩家找日志文件 ✅ 窗口内实时可见
玩家人工操作 删旧整合包、重新下载、覆盖 ✅ 点启动，其余全自动

五、没有改的部分（沿用 McPatch2）

为了保持兼容与稳定，以下完全沿用原项目，没有动：

  • 清单（manifest）的结构与语义
  • 原有的 HTTP / WebDAV / Alist 协议实现
  • 客户端配置文件仍叫 mcpatch.yml（改名会让所有现有用户的配置失效）
  • 内部数据目录 .modsync-temp / .modsync-removed / modsync/
  • Premain-Class 与 javaagent 挂载方式
  • 客户端源码的内部包名 com.github.balloonupdate.mcpatch（避免引入无谓风险）
